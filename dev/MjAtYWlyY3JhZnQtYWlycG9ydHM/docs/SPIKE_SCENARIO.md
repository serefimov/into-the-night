# Контрольный сценарий для первого spike

Эксперимент `norway-autumn-spike`, версия 1, seed `norway-autumn-1`: OSL, **2026-11-20 00:00 UTC**, 30 человек, 10000 кг топлива, 1080 человеко-часов бортовой еды (36 часов экипажа), обслуживание выполнено. Это небольшой воспроизводимый мир для рецензии, а не окончательный каталог или баланс MVP.

Проверены **30 и 90 суток**. Есть два разных безопасных открытия: прямой OSL→LYR и OSL→TOS→LYR с погрузкой в TOS. Оба выдерживают 30 суток даже при нижних границах ещё неизвестных складов. Старт тёмный; первый геометрический восход в OSL — около 07:36 UTC, то есть на выбор и операции есть 7.6 часа. Возможность продолжения после северной зимы остаётся ограничением этого мира.

## Данные и допущения

Статика — [airports.json](../data/spike/airports.json), сценарий, закреплённые версии моделей/конфигурации и видимые диапазоны — [scenario.json](../data/spike/scenario.json). Игровые истинные склады создаёт общий чистый TypeScript-модуль `generateScenario`; в каталоге их нет. Источник координат, класса, регулярного сообщения и ВПП — **OurAirports**, проверено 2026-10-09:

| TOS / ENTC | 69.683296, 18.918900 | 2451×45 | [аэропорт](https://ourairports.com/airports/ENTC/), [ВПП](https://ourairports.com/airports/ENTC/runways.html) |
| LYR / ENSB | 78.246101, 15.465600 | 2319×45 | [аэропорт](https://ourairports.com/airports/ENSB/), [ВПП](https://ourairports.com/airports/ENSB/runways.html) |

[Условия OurAirports](https://ourairports.com/data/): данные в Public Domain, без гарантии точности. Лицензия данных отделена от GPL-3.0-only кода. Это ручная малая выборка; полные CSV не включены. Все три аэропорта имеют регулярное пассажирское сообщение. Игровая пригодность: асфальт, ВПП ≥2000 м, ширина ≥45 м. Смещённые пороги у TOS (392 м), LYR (61/120 м), характеристики конкретного самолёта, погода, рельеф и NOTAM в модель не входят. Список подходит для игрового испытания; он не является эксплуатационным авиационным справочником. Антарктических площадок здесь нет.

Генератор версии 1 применяет FNV-1a к JSON-массиву `[generatorVersion, scenarioId, scenarioVersion, seed, airportId, resource]`, кодовые единицы UTF-16; `u=uint32/2^32`, запас `lo+floor(u*(hi-lo+1))`. Аэропорты сортируются по ID; каждый ресурс имеет собственный ключ. Перестановка каталога не меняет ни запасов, ни мира. Смена seed/версии меняет эксперимент; старые результаты к нему не относятся.

| Аэропорт | Видимое топливо, кг | Видимая еда, человеко-часы | Истинный склад этого seed, кг / человеко-часы |
| --- | --- | --- | --- |
| OSL | 6000–8000 | 2880–3600 | 7611 / 3214 |
| TOS | 8000–10000 | 14400–18000 | 8609 / 17104 |
| LYR | 12000–14000 | 72000–79200 | 13253 / 72509 |

Это вымышленные конечные игровые склады, не сведения о реальных запасах аэропортов. OSL открыт при старте; точные TOS/LYR появляются только после посадки. Прогноз назначения получает видимую проекцию; подстановка разных скрытых запасов не меняет его. Исследовательский CLI намеренно печатает приватные склады — его отчёт нельзя использовать как карточку назначения в интерфейсе.

## Воспроизведение

После `npm ci` и `npm run build` все расчёты работают офлайн:

```sh
npm run spike -- --plan examples/spike/plans/direct-30.json
npm run spike -- --plan examples/spike/plans/via-tos-30.json
npm run spike -- --plan examples/spike/plans/direct-90.json
npm run spike -- --plan examples/spike/plans/seasonal-departure.json
npm run spike -- --plan examples/spike/plans/food-scale-40.json
npm run spike -- --plan examples/spike/plans/revisit.json
npm run spike -- --plan examples/spike/plans/historical-regression.json
npm run spike -- --research
npm run validate:spike
```

`--plan FILE` повторяет фиксированные `input` и `batches`; после каждой посадки следующее планирование идёт отдельным пакетом, уже с раскрытым складом. `confirmRisk: true` в исследовательских планах означает явное разрешение довести опасный опыт до первой гибели; смерть не обходится. CLI возвращает JSON; ошибки аргументов/валидации — код 2, исследовательская гибель — нормальный результат опыта. Для чистого JSON используйте `node scripts/spike-cli.mjs` напрямую.

`--research` повторяет сравнения и ограниченный поиск. `--research --write-report` обновляет свидетельства и отчёты; `--research --verify-report` сверяет вычисленный результат с сохранёнными артефактами (исключается только реальное время вычисления `elapsedMs`). Последняя команда включена в CI. `npm run check` проверяет генерацию, варианты открытия, баланс питания, скрытые склады, сезонную гибель, повторный визит и CLI в разных часовых поясах.

## Что получилось

[Сводный JSON](SPIKE_VALIDATION.json) фиксирует сценарий, конфигурацию самолёта, версии `resources-resume-3` / `meeus-noaa-1` / `great-circle-solar-1`, seed, запасы, бюджет и длительность поиска. Файлы `docs/spike/*.json` содержат действия, точные UTC в миллисекундах, ресурсы и все склады по этапам, журнал событий, солнечные отсчёты, первое предупреждение/поражение. ISO-строка округляется до миллисекунды только для чтения; числовое состояние сохраняет дробные миллисекунды.

| План | Результат |
| --- | --- |
| `direct-30` | 30 суток в LYR; топливо 3959.962 кг, бортовая еда 993.941 человеко-часа |
| `via-tos-30` | 30 суток через TOS, погружено 720 человеко-часов; топливо 3780.735 кг, еда 1696.832 |
| `direct-90` | 90 суток, 2027-02-18 00:00 UTC; до ближайшего Солнца ещё около 10.6 часа |
| `sunrise-threshold` | Автоожидание до 2027-02-17 22:38:34.563 UTC; предупреждение за 12 часов до нижней границы солнечного события |
| `seasonal-departure` | Погрузка 6000 кг / 600 человеко-часов, подготовка, LYR→TOS, обслуживание; безопасно до 2027-02-18 01:16:10.372 UTC |
| `seasonal-limit` | После того же ухода ожидание приводит к солнечной гибели в TOS около 07:14 UTC; предупреждение не даёт долгосрочного убежища |
| `stay-to-180` | При стоянке в LYR Солнце появляется 2027-02-18 10:38:34.577 UTC: прожито около 90.443 суток |
| `revisit` | LYR→TOS→LYR; ранее погруженные 6000 кг и 600 человеко-часов не восстановились, питание продолжило уменьшать склады |

Каждый пакет этих свидетельств проверен полноценным непрерывным валидатором без изменения Солнца или скорости. Сохранение в середине пакета и восстановление дают **точно то же конечное приватное состояние**. Успешные открытия и уход отдельно повторены с нижними границами неизвестных складов: 30/90 суток и безопасная посадка сохраняются. Это проверка выбранных решений по видимым диапазонам; она не доказывает безопасность любого маршрута или всех seed. После открытия нового аэропорта разрешено использовать его известный точный остаток.

Прежняя конфигурация из SCENARIOS пересчитана с прежними координатами и ресурсами как отдельная историческая регрессия, а не импортированный каталог: старт 03:00 UTC, 8000 кг / 180 человеко-часов, склады 6000/720, 8000/1440, 4000/1080. Явный план — OSL→TOS, обслуживание, погрузка **720 человеко-часов**, подготовка, TOS→LYR, обслуживание, ожидание до суток. В конце 1782.851 кг и 796.857 человеко-часа на борту; остатки складов и промежуточные UTC — [в отчёте](spike/historical-regression.json). Прежний текст не задавал объём погрузки; эти результаты относятся к указанному плану, не восстанавливают неизвестные старые действия.

## Баланс и пределы поиска

Сравнение еды LYR **10 / 40 / 100 дней экипажа** сохраняет старт, бортовую еду, топливо, скорость и солнечную модель. При 10 днях автоостановка наступает через 8.510 суток, голод — через 11.510; 30 суток недостижимы именно этим планом. При 40 днях свидетель 30 суток проходит, порог еды наступает через 38.510. При 100 днях первым становится сезонное предупреждение через 89.943 суток. Поэтому диапазон 100–110 дней выбран для исследования зимы и ухода, а не как окончательно принятый баланс. 40 дней уже достаточно для цели 30 суток. Стартовые 10000 кг и 36 часов еды лежат в ранее предложенных диапазонах; исторический старт с 6 часами сохранён отдельно.

На каждом горизонте 30/90/180 суток исследованы два режима: истинные склады и нижние границы неизвестных складов при известном OSL. 30 и 90 суток найдены первым прямым планом. На 180 суток в каждом режиме выполнено **130 кандидатов**: два открытия со стоянкой, затем 128 вариантов одного ухода из LYR. Дни ухода от старта: 30, 60, 75, 85, 89, 90, 120, 150; UTC-часы: 00, 06, 12, 18; назначения TOS/OSL; погрузка 6000 кг / 600 человеко-часов; максимум три перелёта, затем стоянка до цели. В узле сохранены реальные остатки складов; пополнение отсутствует.

Поиск занял примерно несколько секунд в текущем окружении; точные измерения и исходы в JSON. Число кандидатов ограничено, время зависит от машины. Каждый солнечный поиск использует штатный бюджет до 100000 оценок на фазу. Лучший найденный неуспешный план прожил около 90.443 суток; его действия и полный повтор сохранены как `best-180-true-stocks` / `best-180-visible-range-floors`. **180 суток не подтверждены**. Поиск не перебирает произвольные моменты вылета, многократные ночные перелёты и переход полушарий; результат не доказывает непроходимость мира.

Численная точность события — штатные 0.5 с; уточнение до 0.25 с и шага 300 с изменило остановку у предупреждения примерно на 0.00458 с, момент контрольной гибели — на 0 с. Солнечные экстремумы в отчётах — отсчёты с интервалом ≤900 с на каждой записанной фазе, **не точный максимум**; дополнительно записана консервативная верхняя граница через ту же оценку кривизны и вычислительной ошибки, что использует ядро. Безопасность доказана отдельно непрерывным ядром. Физическая ошибка эфемерид отличается от численной скобки: независимая проверка дала максимум направления 0.00839°, полярный пример смещения времени до 455.8 с — см. [SOLAR_MODEL.md](SOLAR_MODEL.md).

Для первого игрового spike доступны выбор прямого/промежуточного открытия, погрузка, месяц стоянки, остановка на пищевом/солнечном пороге, сезонный уход и повторное посещение истощённого склада. После рецензии потребуется решить, даёт ли большой зимний склад интересные решения, и расширить географию для следующего сезона. Этот эксперимент удовлетворяет вычислительному условию 30 суток; окончательный старт MVP ещё не закреплён.
