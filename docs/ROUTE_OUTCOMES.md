# Доступность и итог партии (#42)

Во время выбора общий прогноз проверяет **весь каталог миссии**, независимо от камеры, масштаба, групп и числа отрисованных меток. Текущий аэродром исключён: в текущем мире 1182 направления из 1183 аэропортов. На desktop и mobile видны число подтверждённых доступных перелётов, проверено/всего и осталось. Просмотр карты и проверка не расходуют UTC, топливо или склады.

## Состояния проверки

| Состояние | Значение |
| --- | --- |
| checking | Проверка ещё идёт; отсутствие зелёных меток или подтверждённых рейсов не означает поражение |
| available | Уже есть хотя бы один подтверждённый следующий рейс; оставшиеся направления могут ещё проверяться |
| unresolved | Весь каталог просмотрен, но остаются численно неопределённые варианты; проигрыш не подтверждён |
| failed | Проверку завершить не удалось; партия остаётся открытой, доступна повторная проверка |
| busy | Принят рейс/дозаправка/обслуживание, в том числе пауза внутри операции; анализ следующего шага не выполняется |
| no_safe_choices | Все направления окончательно заблокированы в текущих условиях; возможен отдельный итог no_routes |
| terminal | Уже победа или реальное солнечное поражение; новый тупик не вычисляется |

`complete` означает, что получен финальный ответ для каждого направления. Он не превращает численную неопределённость в безопасность или доказанный запрет. При наличии доступных рейсов партия продолжается, даже если другие варианты неопределённы. Неизвестная будущая причина отказа консервативно остаётся unresolved. Доказанная ресурсная/политическая блокировка достаточна независимо от незавершённой солнечной проверки.

В сводке заблокированное направление учитывается один раз по основной причине: непроверенная полоса, масса, топливо, неоднозначная геометрия, Солнце. Карточка сохраняет полный список причин конкретного вылета. `unverified` — запрет текущего фильтра пригодности, а не эксплуатационное разрешение или выдуманная солнечная смерть.

## Полная проверка и защита от старых ответов

Общая агрегация находится в [mission-availability.ts](../src/core/mission-availability.ts). Worker и запасной расчёт в основном потоке вызывают один [scan-runner.mjs](../web/flight/scan-runner.mjs) и `MissionSession.forecast`. Вход — снимок партии; параметров камеры в нём нет.

[FlightPlanningScan](../web/flight/planning-scan.mjs) связывает ответы с ключом физического состояния и поколением запроса. Ключ учитывает определение сценария/профиля/складов, параметры поиска и фактические UTC/топливо/остатки. При принятии рейса, новом планировании, перезапуске или повторе проверки старый worker отменяется; запоздавшие ответы игнорируются. Выбор другой карточки без изменения физических условий не отменяет общий анализ.

Повтор одинакового результата не увеличивает счётчик. Неизвестные ID, противоречивые ответы и преждевременный `done` не принимаются за полный каталог. При сбое worker автоматически запускается тот же расчёт небольшими порциями в основном потоке; при его ошибке остаётся failed с кнопкой «Повторить проверку».

**Счётчики worker не могут закончить партию.** Если они сообщают окончательный ноль, фактический `MissionSession.resolvePlanning()` заново проверяет полный каталог своим общим прогнозом. Только подтверждённый результат записывается в состояние. Ошибочный all-blocked ответ не побеждает доступный маршрут фактической партии. В рабочем режиме нет ожидания; #25 обязана пересмотреть это правило после появления безопасных действий ожидания.

## Разные исходы

| Статус состояния | result.kind | Сообщение |
| --- | --- | --- |
| won | goal | Цель достигнута |
| dead | sun | Поражение: самолёт встретил Солнце |
| lost | no_routes | Поражение: маршрут оборвался; нет доступных перелётов |
| running | null | Партия продолжается: выбор, выполнение либо незавершённая проверка |

При no_routes сохраняются текущий UTC, топливо и склады; `death` остаётся null. Итог содержит checked/total и основные причины блокировки. В журнал добавляется **один** `mission_lost` на текущем UTC после обязательных фаз предыдущего рейса. Это отсутствие допустимых перелётов **в текущем каталоге и режиме**, не доказательство невозможности для всей Земли, иных самолётов или будущего ожидания. Победа имеет приоритет над поиском следующего рейса: в уже завершённой цели тупик не объявляется.

`availability()` — чистый анализ без изменения партии или доставки событий. `resolvePlanning()` — явная фиксация исхода: при доступности/неопределённости/выполнении/готовом результате ничего не расходует и не доставляет события повторно. Просмотр `stateAt` до UTC результата не показывает будущий итог. Повторное разрешение и загрузка не создают второе событие поражения.

У любого окончательного исхода есть «Начать заново». Это новая партия с исходными данными той же конфигурации: очищаются путь/выбор/журнал, прекращается воспроизведение и отменяется прежняя проверка, камера наводится на самолёт. Это необходимая часть #42, не полная реализация сохранений/экспорта UI из #24.

## Версии и CLI

Текущий режим **airport-flight-v3 / flight-cycle-3**, схема состояния/события/сохранение **3**. Физика полёта и дозаправки #39, профиль, каталог и конфигурация сценария v2 не изменены. Новый формат вводит result, событие mission_lost и сохраняет факт no_routes. Восстановление пересчитывает принятые рейсы и проверяет сам тупик по всему каталогу, а не доверяет записанному счётчику; затем сверяет снимок и курсор доставки событий.

Сохранения mission v1/v2 и survival явно отклоняются до замены текущей партии, без молчаливой миграции. Старые сценарии можно исполнить новым ядром с явным определением и сохранить в v3; это не означает поддержку старого файла сохранения v2.

CLI возвращает ту же availability, state.result и журнал. Коды выхода: 0 — корректное выполнение/незавершённое планирование, 1 — неверный ввод/повреждённые данные, 2 — заблокированный выбор, **3 — подтверждённый no_routes**. При паузе внутри операции возвращается busy, а не поражение. Сохранённый lost восстанавливается с тем же исходом и без повторной доставки события.

Численные отчёты #21/#39 сохраняются на исходных форматах, JSON не переписаны. Генератор academic-westward явно сохраняет исторический формат отчёта v2 и проецирует только прежние события успешного полётного свидетеля в его eventVersion 2; mission_lost в такую проекцию запрещён. Он продолжает проверять те же физические UTC/топливо/склады текущим Session v3. Это совместимость отчёта, не миграция состояния игры.

Chrome проходит desktop/mobile и вложенный Pages-путь; скриншоты доступны в globe-previews.
