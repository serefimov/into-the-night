# Промежуточное состояние, пауза и сохранение

`resources-resume-3`, `SIMULATION_CONFIG.version=3`, `schemaVersion=3`, формат сохранения `SAVE_FORMAT_VERSION=1`. Физические правила Солнца, маршрута, еды и топлива прежние. Активное действие дополнено `elapsedSeconds`; полёт сохраняет фазу, её UTC-границы и фактические координаты. Состояния прежних экспериментальных версий не мигрируются: несовместимость отклоняется с объяснением.

## CLI

После `npm ci` и `npm run build`:

```sh
# Остановить исполнение в середине крейсерского участка и записать сохранение.
npm run simulation -- --plan examples/resource-plan.json --mode execute \
  --stop-at 2026-01-01T21:15:00Z --save /tmp/into-the-night-flight.json

# Продолжить на 123.456 секунды от сохранённого момента, затем снова сохранить.
npm run simulation -- --restore /tmp/into-the-night-flight.json --mode execute \
  --stop-after 123.456 --save /tmp/into-the-night-flight-next.json

# Продолжить до конца принятого плана или первого терминального события.
npm run simulation -- --restore /tmp/into-the-night-flight-next.json --mode execute

# Посмотреть будущее из сохранения без продвижения времени и записи файла.
npm run simulation -- --restore /tmp/into-the-night-flight-next.json --mode forecast

# Сохранить полярное автоожидание через месяц от старта.
npm run simulation -- --plan examples/polar-wait.json --mode execute \
  --stop-after 2592000 --save /tmp/into-the-night-month.json

npm run validate:sessions
```

`--stop-at` принимает строгое UTC ISO с Z (допустимы миллисекунды .sss); `--stop-after` — конечное неотрицательное число секунд от текущего момента. Эти параметры взаимоисключающие. Дробные секунды сохраняются без округления состояния. `--save` разрешён в режиме исполнения; файл записывается через временный файл и атомарное переименование после успешной проверки. Повреждённое восстановление не перезаписывает уже существующее сохранение.

Самодостаточный файл хранит статический мир. При восстановлении можно дополнительно передать `--plan examples/resource-plan.json`: из этого файла используется только ожидаемый `world`, который должен совпасть со сценарием, seed, версией и каталогом сохранения. Самолёт и склады восстанавливаются из сохранения, а не заново из стартовой fixture. `--confirm-risk` нужен при первом принятии опасного плана; принятие риска сохраняется с планом и повторно не запрашивается при продолжении.

## API ядра

```ts
const session = new SimulationSession(world, initialState, actions, { confirmRisk: true });
const preview = session.stateAt(futureUtc); // currentTimeUtc не меняется
const stopped = session.stopAt(shownUtc);  // фиксируется именно shownUtc
const text = serializeSession(session);
const restored = restoreSession(text, world);
const continued = restored.resume();
```

`ForecastTimeline` предоставляет только `stateAt(time)` и `endUtcMs`; прогноз опасного плана доступен без принятия риска. `SimulationSession` проверяет план обычным исполнителем, включая блокировку недостаточного топлива, неопределённости и неподтверждённого риска. Подготовленный будущий результат хранится отдельно от текущего курсора: вычислить конец плана не означает записать его в игровое состояние.

- `stateAt(time)` — независимый просмотр UTC, положения, ресурсов и выполненных к этому времени событий. Не меняет курсор исполнения, склады или курсор доставки событий.
- `current()` — публичный вид текущего зафиксированного момента.
- `stopAt(time)` — продвижение до выбранного момента и пауза. Возвращает `outcome=paused`, пока действие продолжается; активное действие и его прогресс остаются в состоянии. Это пауза принятого плана, а не отмена перелёта или изменение маршрута.
- `resume()` — продолжение до конца рассчитанного плана или первой границы возврата управления.

Просмотр и исполнение ограничиваются первым поражением, остановкой автоожидания или посадкой, требующей раскрытия склада. Если запрошен момент позже этой границы, `requestedUtcMs` сохраняет запрос, а `state.currentTimeUtc` остаётся на фактической границе. Назад исполнять нельзя: для просмотра прошлой даты есть `stateAt`. При численной неопределённости исполняемая сессия не создаётся; прогноз может показать только проверенный префикс.

Виды состояния публичные: скрытые точные склады заменяются диапазонами. Даже `session.stateAt(endUtcMs)` перед посадкой не раскрывает склад назначения. Склад открывается только после реального `stopAt`/`resume`, достигшего посадки. Внутренний `savePayload()` содержит полное состояние для движка и хранения; его нельзя передавать в карточки аэропортов или прогноз интерфейса.

## Журнал

`events` — полный журнал выполненного префикса для отображения истории. У `stopAt`/`resume` дополнительный `newEvents` содержит только ещё не доставленные события: именно его следует использовать для уведомлений. Повторный `stopAt` в тот же момент и повторный `resume` после окончания возвращают пустой `newEvents`. Сохранение удерживает курсор доставки, поэтому продолжение не повторяет подготовку, погрузку, достижения или посадку.

При старте нулевого действия все события этого UTC упорядочены принятой моделью. По одной временной метке нельзя остановиться между одновременными событиями. Смерть по-прежнему имеет приоритет над достижением того же UTC.

## Формат и восстановление

JSON-конверт содержит `formatVersion`, `payload` и `checksum`. В payload:

| Поле | Назначение |
|---|---|
| schemaVersion, simulationVersion, configVersion | Совместимость состояния и правил |
| scenarioId, scenarioVersion, seed, world | Сценарий и статический каталог |
| origin | Исходное внутреннее состояние перед принятым планом, включая конечные склады и открытые сведения |
| actions, options | Принятый план, настройки поиска и подтверждение риска |
| cursorUtcMs, consumedEvents | Фактическая позиция и доставка событий |
| snapshot | Полное состояние в точке паузы: ресурсы, склады, достижения, обслуживание, предупреждения и активное действие/участок |
| journal | Журнал выполненного префикса |

Ключи JSON сортируются; числа IEEE-754 проходят JSON round-trip без потери представимого значения. Контрольная сумма FNV-1a по каноническому JSON обнаруживает случайное повреждение; это не криптографическая подпись и не защита от намеренного редактирования. Сохранение содержит приватные склады; в обычный вывод CLI оно не попадает.

Восстановление проверяет формат, версии, метаданные, диапазоны ресурсов, координаты, ID, флаги, достижения и курсор. Затем заново рассчитывает тот же принятый план из `origin` и сравнивает сохранённый snapshot и журнал с рассчитанным префиксом. Проверка работает в новом объекте сессии; действующая сессия не изменяется при ошибке. Молчаливой генерации нового мира или замены повреждённых ресурсов нет.

Продолжение берёт будущее из расчёта исходного плана, не применяя исполненные передачи к snapshot второй раз. Поэтому разные разбиения одного действия не накапливают ошибки и не меняют солнечное событие. В памяти `stateAt` использует записанные линейные фазы и исходную ортодромию; Солнце не пересчитывается на каждый кадр. Восстановление повторно проверяет принятый план целиком, поэтому его стоимость зависит от длины плана и горизонта поиска. Размер файла зависит от мира и журнала; будущая шкала не сериализуется.

## Проверки и точность

`npm run check` проверяет границы всех фаз, середину полёта, частичную передачу, опустошение склада, месячное ожидание, достижения, одновременные предупреждения, гибель, переход через 180° и полюс. Повреждения проверяются и с заново рассчитанной контрольной суммой, чтобы отдельно проверить содержательные ограничения и согласованность replay. Процессные проверки CLI сравнивают файлы и результаты в четырёх часовых поясах, продолжение из середины полёта и сохранность прежнего файла при ошибке восстановления.

В [SESSION_VALIDATION.json](SESSION_VALIDATION.json) непрерывное исполнение сравнивается с шестью остановками/восстановлениями: итоговые UTC, все ресурсы/склады, раскрытые сведения, достижения и журнал совпадают точно в каноническом JSON, включая числовые значения IEEE-754. Итоговый файл также идентичен. Для промежуточных ресурсов допустимая абсолютная погрешность относительно аналитической формулы — 1e-6 кг или человеко-часа: на 101 точке частичной погрузки измерено около 3.35e-7 кг и 1.10e-7 человеко-часа. Причина — конечное разрешение больших UTC timestamps при вычислении доли фазы. Ресурсы по действиям не округляются. Это не физическая погрешность эфемерид; она отдельно описана в SOLAR_MODEL.md.

Пересчитать отчёт:

```sh
npm run build
npm run validate:sessions -- --write-report
```

Fixture полюса остаётся синтетической проверкой, а не подтверждением длительной стратегии. Кнопки, анимация и браузерное хранилище — следующий spike; этот PR предоставляет вычислительный API и файловый CLI.
