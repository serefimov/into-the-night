# Игровой цикл без еды (#22, обновления #39/#42)

Общий чистый модуль [mission.ts](../src/core/mission.ts) реализует выбор назначения, полёт, обязательные наземные операции и дозаправку под выбранный рейс перед вылетом. Один и тот же `MissionSession` доступен CLI и интерфейсу. Кнопка «Полёт» в #23 вызывает этот API; отдельные команды подготовки/обслуживания/загрузки игроку не нужны.

Режим `airport-flight-v3`, симуляция `flight-cycle-3`, схема состояния 3, события и сохранения 3 отделены от прежнего survival. В состоянии нет еды, голода или бесконечного продовольственного запаса. Нет ручного ожидания, частичной загрузки по выбору или разрешения рискованного рейса. Время при изучении карты стоит; скорость анимации задаёт только частоту продвижения курсора, не физические длительности.

## Конфигурация и контрольные маршруты

Ядро принимает `MissionDefinition`: ID/версию сценария, seed, версии геоданных и складов, профиль самолёта, аэропорты, цель, правило финиша и начальные UTC/топливо/конечные склады. Конструктор копирует данные, проверяет координаты/ID/профиль/покрытие складов и готовность исходного аэропорта. Внешняя мутация определения не меняет сессию.

По умолчанию загружается [academic-westward-v2.json](../data/scenarios/academic-westward-v2.json): Пулково → Толмачёво на запад, старт 1 августа 2026 20:00 UTC, 30000 кг на борту, конечные склады по 64000 кг, seed academic-westward-v2. Полный свидетель и альтернативы — [ACADEMIC_WESTWARD.md](ACADEMIC_WESTWARD.md). Аэропортовый финиш не включает поездку в Академгородок/передачу знаний и не означает завершение всей кампании.

[westward-control-v2.json](../data/scenarios/westward-control-v2.json) — отдельный технический контроль: Сантьяго → Крайстчерч/Сидней/Мельбурн → Перт → Кейптаун, старт 21 июня 2026 21:50 UTC, 30000 кг на борту, склады 64000 кг, SCEL 100000 кг. Профиль/каталог не изменены. [Формула, причины настройки и пересчёт](DEPARTURE_FUEL.md). Старые конфигурация v1 и численные отчёты остаются на старом правиле. Это не утверждение первого сценария научной кампании.

Цель контроля завершается после обязательного обслуживания (`after_service`). Ядро также поддерживает явное `arrival` для конечной посадки без обслуживания. Заправки для ещё не выбранного рейса нет. Прибытие в аэропорт не означает получение знаний в удалённой лаборатории.

## API

| Вызов | Поведение |
| --- | --- |
| `new MissionSession(definition, options?)` | Создать сессию с собственными данными и параметрами солнечной проверки |
| `forecast(id)` | Получить `allowed`, причины и полный прогноз, не меняя время/ресурсы/журнал |
| `fly(id)` | Повторить тот же прогноз и принять только подтверждённый переход; начать выполнение в текущем UTC |
| `current()` | Текущие состояние и уже наступившие события; все остатки топлива публичны |
| `stateAt(utcMs)` | Просмотреть прошлое/будущее уже принятого полёта без изменения курсора или доставки событий |
| `stopAt(utcMs)` | Продвинуть выполнение до указанного UTC, вернуть новые события ровно один раз |
| `resume()` | Завершить уже принятый переход; следующий аэродром автоматически не выбирается |
| `availability()` | Явно проверить доступные направления/неопределённость/тупик, не продвигая время |
| `resolvePlanning()` | Перепроверить полный каталог и зафиксировать только окончательный тупик; незавершённый расчёт не меняет партию |
| `save()` / `MissionSession.restore(text, expectedDefinition?)` | Сохранить/проверить и восстановить сессию, включая середину фазы |

`forecast` и `fly` используют общий `forecastMissionFlight` из mission-flight.ts: ортодромию, профиль расхода/масс и непрерывную проверку всех фаз. Состояния «опасно» и «неопределённо» различаются, оба блокируют запуск. Неизвестный/текущий аэропорт, неоднозначная геометрия, непригодность, топливо/масса, Солнце и незавершённый рейс дают причины отказа без изменения сессии. Направление и широта сами по себе не запрещают полёт.

Прогноз содержит расстояние, UTC прибытия и конца оборота, расход, массы, остатки и заправку, фазы и результат солнечной проверки. Полёт не разрешается только на основании ночной посадки. Возвращаемые данные не являются ссылками на внутреннее состояние.

## Промежуточное состояние

Фазы: необязательная `refuelling` на исходном аэродроме, затем `departure`, `cruise`, `arrival`, `service`; между полётами `planning`, терминально `won`/`dead`/`lost`. `position`, расстояние, топливо, склады и активная фаза относятся к одному показанному UTC. Завершённый физический план предоставлен общим ядром; промежуточный расход распределяется по его фазам и профилю, итоговые границы закрепляются точными результатами перехода.

Во время подготовки заправки топливо ещё не передаётся. Затем оно непрерывно перетекает со скоростью профиля: борт увеличивается на фактически переданную массу, склад на неё же уменьшается. Передача ограничена нужным количеством для выбранного рейса. Недостаток склада/ёмкости блокирует весь переход; уже имеющееся лишнее топливо не удаляется. При пустом складе/нулевой передаче нет дополнительной фазы заправки или цикла нулевых действий. Повторный визит не восстанавливает склад.

Конец полёта не означает раннюю победу, если требуются наземные фазы. `current()` показывает только наступившие события; `stateAt` может показать прогноз будущего до конца принятого плана, не меняя текущий журнал. `stopAt` не перематывает исполнение назад; для просмотра прошлого есть `stateAt`. Запрос времени после конца принятого плана ограничивается его концом: это не скрытое ожидание на земле.

Начальное солнечно опасное состояние сразу даёт реальное событие поражения от Солнца. Подтверждённый рейс уже проверен целиком, поэтому рискованный рейс не исполняется до поражения. Отсутствие безопасных направлений при замороженном времени после полной окончательной проверки — отдельный итог lost/no_routes без выдуманной смерти; `resolvePlanning()` фиксирует его в общем ядре, а `availability()` остаётся чистым анализом. Частичные/неопределённые результаты и busy не завершают партию; `availability` также отдельно сообщает о непроверенных направлениях. Неопределённость Солнца не мешает признать направление заблокированным, если уже доказана нехватка топлива/масса/непригодность.

## Сохранения и события

Новый формат `into-the-night-mission`, версия 3. В нём находятся определение/версии/seed, параметры проверки, последовательность **принятых** назначений, UTC-курсор, курсор доставки событий и снимок. Восстановление проверяет checksum, версии, начальные данные, заново рассчитывает принятые переходы и сверяет текущий снимок/журнал. Оно создаёт новую сессию; повреждённый файл не заменяет живую партию. При переданном `expectedDefinition` требуется точное совпадение определения, включая склады/геоданные.

Для переноса Chrome ↔ Node сравнение снимка допускает финальные двоичные разряды физических метрик: абсолютная разница до 1e−9 для кг/км (топливо, склады, расстояние) и 1e−10 для градусов позиции. Снимок проверяется против заново рассчитанного состояния; UTC, события, результат, остальные поля и checksum остаются строгими. Это не допуск солнечной безопасности и не округление исполнения.

Восстановление пересчитывает историю от исходного состояния, затем возвращается к сохранённому курсору; оно не применяет заправку повторно к снимку. `newEvents` учитывает сохранённый курсор доставки. Старые survival-сохранения, mission v1/v2 и несовместимые версии явно отклоняются до замены живой партии. Общие функции JSON/checksum вынесены в serialization.ts с прежними экспортами из saves.ts; формат старого режима сохранён.

События имеют версию и последовательный номер: `mission_started`, `flight_committed`, `refuelling_started`, `flight_started`, `arrived`, `flight_completed`, `mission_won`, `mission_died`, `mission_lost`. Полный контракт итогов/сканирования/совместимости — [ROUTE_OUTCOMES.md](ROUTE_OUTCOMES.md). Событие начала заправки включает её подготовку, начало передачи определяется временем профиля. Только наступившие события попадают в текущий журнал; повторное продвижение к тому же UTC не доставляет их снова.

## CLI и проверки

```sh
npm run build
npm run mission:cycle -- --path examples/academic-westward/iceland.json
npm run mission:cycle -- --path examples/academic-westward/oslo.json
npm run mission:cycle -- --path examples/academic-westward/copenhagen.json
# Отказ прямого рейса: код выхода 2, состояние остаётся исходным.
npm run mission:cycle -- --path examples/academic-westward/direct-blocked.json
# Пауза внутри первой заправки и сохранение:
npm run mission:cycle -- --path examples/academic-westward/iceland.json --stop-at 2026-08-02T00:10:00Z --save /tmp/mission.json
# Завершить принятый полёт; следующее назначение выбирается отдельно:
npm run mission:cycle -- --load /tmp/mission.json --resume
npm test
```

CLI — второстепенный инструмент повторения, его флаги не являются интерфейсом игры. Файл пути задаёт последовательные решения только после окончания предыдущего перехода; при паузе ещё не принятый остаток списка не попадает в сохранение. Вывод сокращает склады до посещённых аэропортов, API состояния содержит все точные публичные остатки. Неверный ввод даёт код 1, заблокированный выбор — 2, подтверждённый no_routes — 3. Вывод также содержит полную availability и state.result; no_routes сохраняется и перепроверяется при загрузке.

Тесты сравнивают все три прохождения с отдельно сохранённым пересчётом #39 при явном старом определении; новый #21 сверяется со своим эталоном docs/academic-westward, проверяют атомарность отказа, непрерывное состояние, подготовку/перекачку, повторные визиты и пустые склады, границу финиша, неопределённость, тупик, версии/восстановление и однократную доставку событий. CLI воспроизводится в двух часовых поясах и продолжает частично выполненную заправку до того же итога. Новый интерфейс/глобус — #23, игровой браузерный spike и окончательная интеграция сохранений — #24.
