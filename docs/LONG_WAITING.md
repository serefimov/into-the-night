# Длительная стоянка и автоожидание

`resources-resume-3`, `SIMULATION_CONFIG.version=3`, `schemaVersion=3`; отдельная конфигурация ожидания `WAITING_CONFIG.version=1`. Солнце, геометрия и физические параметры ресурсов не изменены. Новое состояние хранит последнее предупреждение `waitingWarning`, чтобы ручное ожидание после него требовало подтверждения. Состояния предыдущей версии автоматически не мигрируются; формат сохранений и проверка совместимости описаны в [SAVE_RESUME.md](SAVE_RESUME.md).

## Воспроизведение

```sh
npm ci
npm run check
npm run simulation -- --plan examples/polar-wait.json
npm run simulation -- --plan examples/polar-wait.json --mode execute
npm run simulation -- --plan examples/polar-wait.json --mode standing
npm run validate:waiting
```

`--mode standing` анализирует исходное положение и запасы, возвращает публичное состояние и прогноз стоянки без расхода игрового времени. Для этого режима необязательный `waitingOptions` задаётся в корне JSON. В плане добавляется действие:

```json
{
  "kind": "auto_wait",
  "options": {
    "foodThresholdCrewHours": 72,
    "sunriseWarningHours": 12,
    "horizonDays": 370
  }
}
```

Все параметры необязательны, приведены значения по умолчанию. Пороги конечные и неотрицательные; горизонт 370–10000 суток. Настройки поиска `eventToleranceSeconds`, `maxIntervalSeconds`, `maxEvaluations` также поддерживаются. Максимум 100000 вычислений по умолчанию делится между последовательными сегментами поиска, а не выделяется заново на каждый месяц. Нулевые резервы разрешены, но не защищают от гибели на самой границе: смерть требует обычного подтверждения риска.

## Сначала физический предел, отдельно уведомление

`forecastStanding({position, startUtcMs, foodPersonHours, crew}, options)` принимает суммарную доступную еду текущего аэропорта и борта. Это не прогноз скрытого склада назначения: анализ разрешён в открытом текущем аэропорту. `searchStationarySunrise(position, utc, options)` работает независимо от запасов.

Первое Солнце ищется на 370 суток с сезонным изменением склонения, последовательными сегментами по 30 суток и общим консервативным валидатором #4. Сегменты проверяются адаптивно, интервал отвергается только по доказанной отрицательной верхней оценке q. Поэтому даже суточный начальный шаг не позволяет пропустить дневной участок между ночными отсчётами. Поиск завершается на первом событии, а не проигрывает весь год после гибели.

`sunrise.status`:

- `found`: есть положительный свидетель q>=0 и интервал первого события; по умолчанию ширина <=0.5 секунды, допустимо <=1 секунды.
- `not_found_within_horizon`: весь доступный горизонт проверен, событие не найдено; это не утверждение «никогда».
- `indeterminate`: не удалось разрешить касание/близость горизонта либо исчерпан бюджет. Это не доказательство гибели или безопасности остальной стоянки.

Прогноз показывает запрошенный конец, доступный конец, проверенный безопасный префикс и `rangeLimited`. При выходе за диапазон модели 2020–2040 поиск ограничен последним представимым поддерживаемым UTC. Например, для северного полюса 2040-12-01 Солнце не найдено до конца модели; прогноз прямо сообщает укороченный горизонт. Бесконечная стоянка не обещается.

`maximum` — физическая граница по первому из голода и Солнца. При голоде внутри солнечного интервала поиск повторяется лишь до голода, чтобы правильно определить порядок событий. `status=limited` означает найденный предел; `horizon_limited` — только границу проверенного диапазона; `needs_refinement` — неопределённость. `seconds` считается от `sunrise.startUtcMs`; `boundaryUtcMs` — терминальная граница, выживание в этот самый момент не обещается. При солнечном ограничении отдельно передаются интервал события и доказанный безопасный префикс.

Автоожидание вычисляет:

- Еда: `max(0, (foodPersonHours / crew - foodThresholdCrewHours) * 3600)` секунд.
- Солнце: начало интервала первого события минус `sunriseWarningHours`; остановка не позже чем за указанный запас до любой точки этого интервала.

Берётся первый порог. Одновременные пороги создают оба события `food_threshold` и `sunrise_warning`. `automatic.maximumRemainingSeconds` показывает остаток до физической границы в момент автоматической остановки (или null, если глобальный предел не установлен). Солнечная остановка может быть раньше формульного момента по свидетелю максимум на ширину его интервала.

При достигнутом пороге `alreadyReached=true`: время не двигается, новая перемотка не запускается. `waiting_stopped` возвращает управление и не исполняет последующие действия того же плана. Для продолжения нужен новый план. Если Солнце не найдено, остановка ограничивается проверенным горизонтом с запасом до потенциального предупреждения за его пределами; можно пересчитать следующий горизонт. При неопределённости, мешающей определить первый порог, исполнение возвращает `needs_refinement` с исходным состоянием. Если ранний порог еды уже доказан, дальняя неопределённость Солнца не мешает остановиться на нём.

## Исполнение и ограничения

Автоожидание использует обычное аналитическое питание: сначала склад, затем борт, без топлива на земле. Еда не грузится на борт автоматически; обслуживание/подготовка не выполняются; полярная стоянка не имеет искусственного лимита. Достижения сохраняются без сброса мира. Прогноз и исполнение совпадают для известных данных и не мутируют вход. Метаданные `waiting` относятся к началу анализируемого действия, итоговые остатки — к UTC возвращённого состояния.

После выданного предупреждения ручное `wait` требует `confirmRisk: true` даже если выбран короткий физически безопасный отрезок. Предупреждение сохраняется на этой стоянке и сбрасывается при вылете. Опасное обслуживание и другие операции всегда проверяются обычным исполнителем; предупреждение не останавливает Солнце. Ни двенадцатичасовой запас, ни событие предупреждения не гарантируют безопасный путь отхода.

Физическая ошибка эфемерид отличается от численной ширины события; см. SOLAR_MODEL.md. У полюса слишком строгий допуск может оказаться недостижим при консервативной оценке погрешности q: контроль с допуском 0.1 с возвращает `indeterminate`, а 0.25/0.5/1 с дают согласующийся первый восход. Реальное почти касательное дневное освещение также проверено: неразрешённое касание не заменяется более поздним обычным восходом. Пределы консервативного поиска не ослаблялись ради положительного результата.

## Измерение

Машиночитаемый отчёт первоначальной реализации #6 (`resources-waiting-2`) — [WAITING_VALIDATION.json](WAITING_VALIDATION.json). Физические правила не изменились; команда валидации проверяет текущую версию. Повторить и обновить именно измерение:

```sh
npm run build
npm run validate:waiting -- --write-report
```

Окружение контрольного измерения: Node 24.19.0, Linux 6.18.44 x64, AMD EPYC 9V74; окружение показывает 3 логических CPU. Девять повторов после двух прогревочных. Поиск с горизонтом 370 суток до первого восхода на северном полюсе: медиана около 6.3 мс, 11653 вычисления, пять месячных сегментов. Ручной запрос ожидания 370 суток: медиана около 12.6 мс; первый терминальный момент — Солнце через 120.85 суток, дальнейшее ожидание не рассчитывается. Полное автоожидание с прогнозом и исполнением: медиана около 22.8 мс. Это замер данного окружения, не ограничение времени CI.

Полюса в fixture — синтетические точки для геометрии, не реальные аэропорты. Запасы 100000 человеко-часов выбраны для проверки сезонного восхода, не для баланса игры. Лонгйир проверяется только геометрически. Проходимость маршрутов на месяцы эти испытания не доказывают. Остановка в выбранном UTC, `stateAt` и сохранение/продолжение активного действия реализованы в #7: [контракт](SAVE_RESUME.md). Кнопки и анимация остаются в spike.
