# Исполнение плана и ресурсы

Текущая версия `resources-waiting-2`, конфигурация `SIMULATION_CONFIG.version=2`, schemaVersion=2. Базовый исполнитель ресурсов появился в `resources-1`; физические параметры не изменены. Общий TypeScript-модуль не использует DOM, часы ОС, сеть или случайность. Модель Солнца и консервативный поиск события переиспользуются из #3/#4; ошибка солнечного события ограничена выбранным допуском (по умолчанию 0.5 секунды). Физическая ошибка эфемерид описана отдельно в SOLAR_MODEL.md.

## Запуск

```sh
npm ci
npm run check
npm run simulation -- --plan examples/resource-plan.json
npm run simulation -- --plan examples/resource-plan.json --mode execute
```

JSON содержит `world` (версии сценария, seed, статические аэропорты с диапазонами складов), `stocks` (истинные начальные запасы), `utc`, `airportId`, `aircraft`, необязательный `serviced` и `actions`. Это исследовательский вход CLI; в браузер нельзя передавать весь исходный JSON с приватными складами. Пример OSL→TOS — проверка одного перелёта, не доказательство длительной стратегии.

Действия:

| kind | Параметры | Условие |
|---|---|---|
| load | fuelKg, foodPersonHours | Количество передачи, не целевой остаток; не больше исходного склада и свободной вместимости |
| prepare | — | После обслуживания; 15 минут; требуется перед каждым вылетом |
| fly | destinationId | Подготовка выполнена, топлива достаточно на всю дугу |
| service | — | После посадки один раз; 15 минут |
| wait | seconds | Ручное ожидание, конечная неотрицательная длительность |
| auto_wait | options (необязательно) | До первого уведомления или границы поиска; возвращает управление |

Загрузка и ожидание разрешены до обслуживания. Перелёт включает 15 минут взлёта, движение 850 км/ч и 15 минут посадки. Только движение расходует 3 кг/км. Экипаж из 30 человек питается постоянно: 30/3600 человеко-часа в секунду. На земле сначала склад, в воздухе только борт. Бак 18000 кг; бортовая еда 2160 человеко-часов. Погрузка 1.2 человеко-часа/с, заправка 200/60 кг/с; потоки заканчиваются независимо.

## Контракт и сведения

`createSimulation(world, stocks, utc, airportId, aircraft, serviced)` проверяет исходные запасы, координаты и версии. Стартовый аэропорт открыт. `forecastPlan` возвращает публичное состояние и события, `executePlan` — внутреннее состояние для движка. В UI/вывод CLI передавать только `visibleState(world, state)`: скрытые точные склады заменяются исходными диапазонами. Входные объекты не мутируются.

Прогноз проверяет точное известное продолжение, включая весь перелёт и бортовые ресурсы. После первой посадки в новый аэропорт остаток плана получает `needs_discovery`: прогноз не использует скрытый склад и не раскрывает его. Исполнение также возвращает управление при этой посадке и раскрывает фактические запасы; затем можно передать оставшиеся действия новым планом. Если перелёт был последним действием, результат `completed`, но склад в прогнозе остаётся диапазоном. Это необходимая граница точного прогноза при скрытых запасах; многозвенная цепочка через уже открытые аэропорты исполняется целиком. Посадка не восстанавливает склад.

`validation_error` откатывает весь переданный план: первоначальное состояние, пустые события, пояснение ошибки. Подтверждение риска не разрешает вылет с недостаточным топливом. План с предсказанной гибелью возвращает при исполнении `risk_confirmation_required` с причиной и UTC. Продолжить можно только с `confirmRisk: true` (`--confirm-risk` в CLI). Сам прогноз показывает терминальное состояние и `death`. Численная неопределённость возвращает `needs_refinement`; исполнение в этом случае сохраняет исходное состояние.

## События и границы

Линейные ресурсные события считаются аналитически. Погрузка делится по завершению потоков и опустошению еды склада; питание вычитается одновременно с передачей. `loading_limited` сообщает непереданную еду, `loading_completed` — фактическую передачу. При гибели `activeAction` сохраняет запрос, время начала и переданные количества, `activeFlight` — фазу и границы участка, положение — координаты в момент остановки.

Солнечный поиск ограничен первым ресурсным событием и сохраняет исходную траекторию. Поэтому поздний солнечный свидетель не перекрывает более ранний голод. При одновременно обнаруженном Солнце и ресурсном событии первым записывается солнечное поражение. При совпадении поражения и достижения поражение имеет приоритет. Ноль топлива точно в конце движения разрешён; ноль доступной еды — гибель немедленно. Достижения 30/90/180/365 суток добавляются в журнал и не сбрасывают мир.

Состояние ресурсов не округляется по действиям. UTC представлен JS `number` в миллисекундах, включая дробную часть; у современных дат его разрешение около 0.000244 мс. На аналитических границах расход считается по исходной длительности, чтобы вычитание больших timestamps не накапливало дополнительную ошибку. Длительности ниже представимого разрешения отклоняются. Числа отображения можно округлять только за пределами ядра.

Автоожидание и предупреждения 72 часа еды / 12 часов до Солнца реализованы в #6: [контракт](docs/LONG_WAITING.md). Последнее предупреждение хранится в `waitingWarning`; ручное ожидание после него требует явного подтверждения риска. Сериализация, `stateAt` и продолжение прерванного активного действия — #7. Генерация аэропортов и seed-зависимых запасов, поиск длительных стратегий — #8; сейчас мир задаёт явная fixture. CLI печатает JSON; код 2 означает ошибку входа, остальные исходы различаются по `outcome`.
